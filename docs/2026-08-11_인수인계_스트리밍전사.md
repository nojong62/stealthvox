## §1 현황 — 지금 코드에 있는 것

### 1.1 유저 음성 → 글자

**Circle Talk(`routine_mode_anyone.dart`)과 Scenario Talk(`routine_mode_roleplay.dart`)**
두 모드는 OpenAI 스트리밍 전사로 갈아탔다.

```
마이크 24kHz PCM16
  → wss://api.openai.com/v1/realtime?intent=transcription
     session.update { type: "transcription", model: gpt-4o-transcribe, language: ko }
     turn_detection: server_vad (threshold 0.5 / prefix 300ms / silence 600ms)
  → input_audio_buffer.speech_started / speech_stopped
  → conversation.item.input_audio_transcription.delta      ← 화면 임시 말풍선 전용
  → conversation.item.input_audio_transcription.completed  ← 유저 턴 확정 (유일)
  → 그 아래는 기존 코드 그대로 (노이즈 게이트 → AI 응답 → tts-1 → History)
```

**⚠️ 이름 주의.** 이 앱에서 "리얼타임"은 2026-08-08에 걷어낸 **음성 대화
WebRTC(`gpt-realtime`)** 를 가리키는 말이다. 지금 것은 전사 통로일 뿐이고
글자를 만드는 모델은 예전과 같은 `gpt-4o-transcribe`다. 코드·커밋·브랜치에서
`streaming`으로 부른다. 소켓 주소의 `/v1/realtime`만 OpenAI가 정한 것이라
못 바꾼다. **Duo의 `first_turn_realtime_voice.dart`는 진짜 Realtime 음성이라
이름이 맞다 — 건드리지 말 것.**

**Step Expand(`routine_mode_step_expand.dart`)는 아직 Deepgram·16kHz 그대로다.**
세 모드가 지금 서로 다르다.

| 파일 | 역할 |
|---|---|
| `services/openai_streaming_transcribe_session.dart` | 전사 소켓. **플래그·모델·VAD 3값이 전부 이 파일 상단 상수** |
| `services/openai_streaming_transcribe_prewarm.dart` | 방 진입 전 소켓 예열 |

### 1.3 플래그

```
kFreeTalkUseStreamingStt   (openai_streaming_transcribe_session.dart)
  기본 ON. flutter run --dart-define=FREETALK_STREAMING_STT=false → 옛 Deepgram 경로
```

두 엔진은 **절대 동시에 안 돈다.** 예열도 켜진 쪽만 한다.
소켓 연결이 **아예 실패한 경우에만** Deepgram으로 폴백하고,
그때 `🛟 [STT-FALLBACK]`이 찍힌다 — 이 줄이 보이면 그 턴 측정값은 버린다.

### 1.4 반드시 지켜야 할 불변식

- **`speech_stopped`에서 AI 파이프라인을 시작하지 않는다.** 발화 종료 신호일
  뿐이다. 유저 턴 확정은 `transcription.completed` **한 곳**이다.
- **`delta`는 화면 전용.** 파이프라인·History·턴 카운트에 닿으면 안 된다.
- **중복 방어선은 OpenAI `item_id`.** 전사문 해시는 item_id가 빈 예외에만.
- **샘플레이트 24000은 세 곳이 같아야 한다** — 녹음 RecordConfig / Deepgram URI
  `sample_rate` / 폴백 `transcribePcm16(sampleRate:)`. 한 곳만 어긋나면 에러가
  아니라 "이상한 문장"으로 나와서 원인을 못 찾는다.
- **소켓은 방 세션 내내 유지.** 턴마다 여닫는 것은 녹음과 오디오 게이트뿐이다.
  녹음은 매 턴 닫아야 한다 — Android는 녹음 세션이 열려 있으면 AI 음성 출력
  라우팅을 뒤늦게 덮어쓴다.
- **AI가 말하는 동안 마이크를 열지 않는다.** Circle Talk은 `echoCancel`이 꺼져
  있다. `_ttsAdapter.isBusy`만으로는 부족하다 — 오프너 문장을 gpt-4o-mini가
  만드는 구간에는 아직 재생 전이라 `isBusy`가 false다. `_isAiOpenerPlaying`
  가드가 그래서 있다(2026-08-11에 마이크가 오프너보다 7.7초 먼저 열렸다).

### 1.5 AI 응답 (Circle Talk)

`UnifiedBrain.streamCircleMemberTurn` — `stream: true`로 받되 **다 모아서 한 번에
읽는다.** 스트리밍으로 받는 이유는 `AI_TEXT_FIRST_TOKEN`을 재기 위해서다.
모델 `gpt-4o-mini`, temperature 0.75, max_tokens 120.

**AI 페르소나는 서클의 총무**다 — 정보통·소식통·수다장이. 진행자가 아니다.
프롬프트는 `_buildCircleMemberInstructions()` 한 곳(12,244자).
2026-08-11에 세 블록의 의미 중복을 압축했다(13,776 → 12,244자). **기능은 안 뺐다.**

### 1.6 모드마다 TTS가 다르다 (중요)

| 모드 | TTS 구현 | 방식 |
|---|---|---|
| Circle Talk | `TtsAdapter` | **pcm 스트리밍** + 프리롤 + 연결 풀 |
| Scenario Talk | `TtsQueueManager` | **mp3 통파일** → 다 받은 뒤 재생 |
| Step Expand | `TtsQueueManager` | 같음 |

**Circle Talk 기준으로 잰 지연 분해를 다른 모드에 옮기지 말 것.**

## §2 실측 — 실기기 SM S931N (Android 16)

### 2.1 유저 음성 → 글자 확정 (speech_stopped → completed)

| 모드 | 범위 | 평균 |
|---|---|---|
| Circle Talk | 356~878ms | ~520ms |
| Scenario Talk | 384~586ms | ~477ms |

예전 경로는 Deepgram endpointing 700ms + 앱 대기창 700ms를 **글자를 만들기도
전에** 썼다. 그 1.4초가 사라졌다.

**부분 전사(delta)는 말하는 도중에 오지 않는다.** 8~12조각이 오지만 전부
`speech_stopped` **이후 0.1~0.4초**에 몰려온다. `gpt-4o-transcribe`는 버퍼가
commit된 뒤 전사하는 모델이다. 화면에 글자가 뜨는 시점이 절반으로 앞당겨진
것이 실제 효과이고, "말하는 중에 자라는" 것은 아니다.
말하는 중 부분 전사를 원하면 `gpt-live-transcribe`로 바꿔야 한다
(`kStreamingSttModel` 한 줄). **재실험 금지 — 이미 로그로 확인했다.**

### 2.2 AI 응답 분해 (Circle Talk, 발화 종료 기준)

| 턴 | STT | GPT 첫 토큰 | GPT 생성 | TTS API | 프리롤 | 첫 소리 |
|---|---|---|---|---|---|---|
| 1 | 477 | 1353 | 191 | 1251 | 216 | 3457ms |
| 2 | 491 | 613 | 104 | 1382 | 127 | 2667ms |
| 3 | 356 | 1002 | 144 | 1784 | 340 | 3564ms |
| 4 | 506 | 611 | 109 | 2452 | 400 | 4082ms |

**gpt-4o-mini는 첫 토큰까지 0.6~1.4초 침묵하다가 나머지를 0.1~0.2초에
쏟아낸다.** 생성 시간이 아니라 TTFT가 비용이다.

**tts-1은 요청→첫 바이트가 1.25~2.45초**로 널뛴다. 같은 길이 요청에 2배 차이.
글자 수와 상관없다(12자 1784ms, 21자 1382ms).
세션 첫 TTS는 항상 느리다(2.5초) — 연결이 데워지면 1.2초대.

### 2.3 틀린 것으로 판명된 가설 — 반복하지 말 것

- **프리롤 0.75초가 병목이다** → 아니다. `prerollBytes = 36000`은 0.75초짜리
  *오디오 분량*이지 *지연*이 아니다. 서버가 실시간보다 빠르게 보내서 벽시계로는
  127~400ms(전체의 5~9%)만 걸린다. 줄여도 100ms 남짓 아끼고 끊김 위험만 산다.
- **큐 대기가 있다** → 없다. `queuedMs=0~6`.
- **연결 풀 워밍업 실패가 상시 문제다** → 아니다. 앱 콜드 스타트에 한 번
  5초 타임아웃이 났고, 정상일 때는 498~839ms로 성공한다.
- **어댑터 로그의 `ttfbMs`** → **믿지 말 것.** 스톱워치가 `client.send()` 반환
  *뒤에* 시작해서 0~4ms로 찍힌다. 진짜 TTFB는 `TTS_REQUEST_SENT`와
  `TTS_FIRST_CHUNK` 두 로그의 **시각 차**로 구한다. (미수정)

## §3 폐기 — 해보고 되돌린 것

### 3.1 AI 응답 조각내어 먼저 읽기 (`fe78cae0` → `961bbcd7`로 되돌림)

첫 의미단위가 완성되면 그 조각만 먼저 TTS로 보내 GPT 생성과 TTS를 겹치려 했다.

**실패했다. 음성이 끊겼다.** 유저 표현: "몇 마디 하고 뜨문뜨문 말했어."

```
1조각 다 먹임 → 버퍼에 오디오 0.9~1.3초 남음
그제서야 2조각 TTS 요청 발사 → tts-1이 1.2~3.4초 걸림
→ 재생기가 1.4~2.1초 말라붙음
```

겹쳐서 아낀 시간은 **37~66ms**뿐이었다(§2.2의 TTFT 구조 때문).
짧은 응답에서는 분할기가 끊을 자리를 못 찾아 아예 작동하지 않았다.

**되살리려면 뒤 조각 TTS를 큐가 아니라 병렬로 미리 쏴야 한다** — 어댑터에
`TtsPrefetch` / `speakPrefetched`가 이미 있다. 그 전에는 손대지 말 것.
이 조건은 `_processCircleTalkTurn` 주석에도 박아 뒀다.

## §4 미착수 — 코드에 **없다**. 제안일 뿐이다

### 4.1 Step Expand 전사 전환

유일하게 Deepgram·16kHz로 남은 모드. Scenario Talk 이식(`b7bbc5aa`)을 그대로
따라 하면 된다. 주의: 이 모드는 `_startUserListening()`이라는 다른 재시작
함수를 쓰고, `echoCancel: true` / `noiseSuppress: true`가 켜져 있다.

### 4.2 Scenario Talk TTS를 mp3 통파일 → PCM 스트리밍으로

지금은 **합성이 다 끝나야 소리가 난다**. Circle Talk의 `TtsAdapter`가 검증된
구조다. 겹치기가 아니라 없던 스트리밍을 넣는 것이라 실제 이득이 있다.
**Circle Talk에서 실패한 조각내기와 혼동하지 말 것 — 다른 작업이다.**

### 4.3 부분 재확인 (Selective Clarification) — 설계만 있음

전체 문장 재요청 대신 **불확실한 슬롯만 되묻기**.
사용자 지시 원문: 목적어 불확실 → "뭘 들다가 다치셨다고요?" / 장소 → "어디에서" /
사람 → "누구랑" / 시간 → "언제부터" / 행동 → "뭘 하다가" / 수량 → "몇 개".
AI가 추측해서 고치면 안 되고, 유저가 "역기요" 하면 나머지와 결합해 확정한다.

조사 결과 반드시 알아야 할 것:
- **Circle Talk에는 되묻기가 아예 없다.** `KoreanTurnValidator`를 2026-08-09에
  걷어냈다(멀쩡한 문장을 세 번 연달아 반려해 유저가 갇혔다).
- **비슷한 코드가 있지만 전부 죽은 코드다.** `[HEARD_CONFIRM]` / `[CLARIFY]` /
  `[GARBLED]` 태그 체계가 Step Expand·Scenario Talk에 있는데 전부
  `_processRelayPipeline` 안이고, 그 유일한 호출부가
  `_commitAndProcessLegacy`(`// ignore: unused_element`)다. 상태 기계(보류 →
  확인 → 재개)는 설계 참고로 쓸 만하다.
- **STT 신뢰도 축이 없다.** `gpt-4o-transcribe`는 word confidence를 안 준다.
  다만 세션 설정에 `include: ["item.input_audio_transcription.logprobs"]`를
  넣으면 토큰별 logprob이 온다. ②문맥 판정만으로도 "옛길을 들다가"는 잡힌다.
- 되묻기는 질문이라 `[ASK SOMETIMES]` 규칙과 부딪힌다. 발생률 상한이 필요할 수 있다.

### 4.4 프롬프트 압축 효과 검증 (진행 중, 미검증)

## §5 로그 태그 사전

| 태그 | 의미 |
|---|---|
| `✅ [STREAM-STT] connected` | 소켓 + session.update 성공 (서버가 확인해 준 것) |
| `❌ [STREAM-STT-ERR]` | 서버 에러 **원문**. 스펙 불일치는 여기서 갈린다 |
| `📡 [STREAM-VAD]` | speech_started / speech_stopped / committed |
| `🎙️ [STREAM-GATE]` | 오디오 전송 open/close |
| `🖼️ [STREAM-DELTA] first` | 부분 전사 첫 조각 도착 |
| `[ANY-STT]` / `[SCN-STT]` | 유저 턴 확정 (Circle / Scenario) |
| `🎧 [STT-ROUTE] ... deltas=N` | 확정. `deltas=0`이면 미리보기가 없었다 |
| `⏱️ [PERF] engine=streaming X=+Nms` | **발화 종료 기준** 타임라인 |
| `📏 [AI-TOKENS]` | promptTokens / cachedTokens / systemPromptChars |
| `⏱️ [TTS-PERF] TTS_REQUEST_SENT` | 요청이 소켓에 나간 순간 + queuedMs |
| `⏱️ [TTS-PERF] TTS_FIRST_CHUNK` | 첫 오디오 바이트 (**ttfbMs 값은 못 믿음**) |
| `🔊 [TTS-ADAPTER] playback_start` | 재생 시작. startMs − 첫 청크 = 프리롤 |
| `🛟 [STT-FALLBACK]` | Deepgram으로 떨어짐. **그 턴 측정값 무효** |

한 턴 재는 법:

```
USER_KOREAN_FINAL   STT 끝
AI_REQUEST_START
AI_TEXT_FIRST_TOKEN ← 여기까지가 TTFT (가장 큰 GPT 비용)
AI_TEXT_COMPLETE
TTS_ENQUEUE
TTS_REQUEST_SENT ─┐
TTS_FIRST_CHUNK  ─┴ 이 둘의 시각 차 = 진짜 TTS TTFB
playback_start      startMs − 첫 청크 = 프리롤
AI_FIRST_AUDIO      첫 소리
```
