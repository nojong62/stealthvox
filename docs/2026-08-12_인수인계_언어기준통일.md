## §1 목표

로비에서 고른 두 값이 모든 대화방과 히스토리의 유일한 기준이 된다.

| 값 | 뜻 | FFAppState |
| --- | --- | --- |
| ORIGIN | 사용자가 **실제로 말하는** 언어 | `nativeLang` (기본 `'Korean'`) |
| TARGET | 변환·학습할 언어 | `targetLang` (기본 `''`) |
| 보이스 | 음색만. **언어에 관여하지 않는다** | `aiVoice` (기본 `'echo'`) |

지금은 세 모드(Circle Talk / Scenario Talk / Step Expand)의 **전사기가 한국어로
고정**돼 있다. 반면 AI 응답 프롬프트는 이미 로비 ORIGIN을 쓴다
(`buildNativeOutputLanguagePolicy(FFAppState().nativeLang)`).

> **즉 ORIGIN=Japanese면 지금은 이렇게 된다:**
> 유저가 일본어로 말함 → 한국어로 전사(오인식) → AI만 일본어로 답변.
> 전사 예열도 `ja`로 뜨는데 소비처가 `ko`로 집어가 **항상 불일치 → 예열 100% 낭비**.

**건드리지 말 것**

- `step_expand:1424` 연습용 Deepgram은 **TARGET**을 쓴다. 유저가 타겟 문장을
  따라 말하는 구간이라 지금이 맞다.
- `step_expand:330` 정밀 재전사는 이미 로비 ORIGIN을 쓴다.
- 세 모드의 `target_lang` 저장은 이미 로비 TARGET이다.

로비에서 언어를 바꿔도 잘못된 언어의 세션이 채택될 일은 없다.

**Phase A 커밋 후 확인**: ORIGIN=Korean이면 로그의 언어 코드가 전부 `ko`로
지금과 완전히 동일해야 한다.

### Phase B — 번역 프롬프트 다국어화

**12개 언어 팩을 만들지 않는다.** 공통 다국어 프롬프트 + 한국어 조건부 보정.

현재 세 모드의 `streamUserTranslation` 프롬프트가 한국어 전용으로 설계돼 있다.

| 파일 | 위치 | 한국어 전용 요소 |
| --- | --- | --- |
| anyone | `:6633` | `"Korean-to-$targetLang"`, pro-drop 설명, 조사(은/는/이/가) 판별, 한국어 예문 6개(`:6666-6670`) |
| anyone | `:6647` | 되묻기 출력이 한국어 고정 `제가 잘못 들었나요? …` |
| anyone | `:6704` | `"Translate the first Korean utterance…"` |
| roleplay | `:5175` | `"Korean-to-$targetLang"`, 정정 신호가 한국어 문자열 목록 |
| step_expand | `:6340` | `"translating Korean to $targetLang"`, 동일한 한국어 정정 목록 |

**바꿀 구조**

1. 공통 프롬프트에 **입력 언어 = ORIGIN**, **출력 언어 = TARGET**을 값으로 전달
2. 생략·어순·관용 표현은 "해당 언어의 문맥으로 복원"이라는 일반 규칙으로
3. 핵심 단어를 지어내지 않음. 확신 없으면 **ORIGIN 언어로** 구체적으로 되물음
4. ORIGIN이 Korean일 때만 기존 조사·생략·정정 규칙과 예문을 **보조 블록으로 덧붙임**
5. 정정 감지: 한국어 문자열 목록에 의존하지 말고 "이전 발화를 수정·부정·대체하려는
   의도인가"를 모델이 문맥으로 판단. Korean일 때만 기존 신호어를 보조로 제공

**되묻기 예시** — ORIGIN Korean이면 "무엇을 들다가 다치셨다고요?",
Japanese면 일본어로 같은 의미, English면 영어로.

**Circle Talk의 한국어 전용 함수** — 이름만 바꾸지 말고 내부를 조사한 뒤 수정한다.
내부가 이미 동적이면 근거를 적고 이름만 정리, 실제로 한국어 고정이면 동적으로 바꾼다.

- [ ] `generateKoreanOpener` (`anyone:5189`) — 프롬프트가 `Korean 해요체 존댓말` 고정
- [ ] `rewriteToNaturalPoliteKorean` (`anyone:3798` 호출)
- [ ] `kKoreanPoliteSpeechPolicy` (`anyone:1463` 사용)
- [ ] `translateKoreanToTarget` (`anyone:3822`, `:3892`)
- [ ] `myTarget: 'Korean'` (`anyone:3738`) — AI 원문 언어를 ORIGIN으로

목표 상태: **AI 대화 원문 = ORIGIN / 화면 학습 변환문 = TARGET /
AI 음성 = ORIGIN 문장 / 히스토리 학습 음성 = TARGET 문장.**

## §4 검증

Phase A 커밋 → Phase B 커밋 → **합친 상태에서** 아래를 본다.

| 조합 | 확인 |
| --- | --- |
| Korean → English | 현재와 완전히 동일 (회귀 없음) |
| Korean → Japanese | 전사 ko, 변환문 일본어 |
| Japanese → English | **전사 ja**, 변환문 영어 |
| English → English | 동일 언어 — **번역 API 호출 없이 원문 복사** |

추가로:

- 로비에서 ORIGIN 변경 후 예열 언어가 일치하는지 (로그 `[STREAM-PREWARM] adopted lang=`)
- 각 모드 전사 결과 / AI 응답 언어 / 화면 TARGET 문장
- 히스토리 `native_lang`·`target_lang` 기록값과 재진입 후 유지
- 번역·TTS 캐시가 깨지지 않는지
- 보이스를 바꿔도 언어가 안 바뀌는지

**캐시 주의점**: `TtsCache._key(text, voice)`는 텍스트를 키에 넣어 언어 충돌이
없다. 그러나 히스토리 첫 페이지 소리듣기의 디스크 캐시 키는
`tts1_nova_native_$msgId.mp3` (`chat_history_master.dart:3105` 부근)로
**TARGET이 키에 없다.** 같은 msgId의 `translated_text`를 다른 언어로 다시
만들면 옛 오디오가 나온다. 현재는 비어 있는 줄에만 1회 생성돼 발생하지
않지만, 재생성 경로를 만들면 키에 TARGET을 넣어야 한다.

**손대지 말 것**: Duo 통신·과금·세션 롤오버·발화 종료 판정.
