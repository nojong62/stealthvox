## Play Integrity API 토큰 검증 구조

**직접 구축해야 합니다** — 단, Google이 검증 API를 제공해줘서 로직 자체는 단순합니다.
### 흐름 구조

```
앱(Flutter) → Google 서버 → 토큰 발급
     ↓
개발자 백엔드(Cloud Functions) → Google API로 토큰 검증
     ↓
결과 반환 → 앱에서 허용/차단 처리
```

---

### 역할 분담

| 주체 | 역할 |
|------|------|
| **Google** | 토큰 생성 API, 토큰 검증 API 제공 |
| **개발자 (Cloud Functions)** | 검증 요청 보내고 결과 해석하는 로직 작성 |
| **Flutter 앱** | 토큰 요청 → 백엔드로 전송 |

### StealthVox 기준 체감 난이도

StealthVox는 이미 **Cloud Functions 인프라가 갖춰져 있어서** 추가 서버 구축 없이 함수 하나만 추가하면 됩니다. `revenueCatWebhook`이나 `claimWelcomeBonus` 같은 기존 패턴 그대로 적용 가능.
### 지금 당장 필요한가?

런칭 초기엔 **불필요**합니다. 크레딧 조작 시도나 비정상 사용 패턴이 실제로 나타날 때 추가하는 게 현실적입니다. Firestore 보안 규칙 강화가 더 우선순위가 높습니다.
==============================
firebase 보안 규칙 - 최종 수정

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    
    // chat_history는 본인만
    match /users/{uid}/chat_history/{room} {
      allow read, write: if request.auth.uid == uid;
      
      match /messages/{msg} {
        allow read, write: if request.auth.uid == uid;
      }
    }
    
    // sessions는 본인만
    match /users/{uid}/sessions/{session} {
      allow read, write: if request.auth.uid == uid;
      allow delete: if false;
    }
    
    // purchases는 본인만 (이미 OK)
    match /users/{uid}/purchases/{doc} {
      allow read, write: if request.auth.uid == uid;
    }
    
    // users 본문은 본인만
    match /users/{uid} {
      allow read, write: if request.auth.uid == uid;
    }
    
    // rooms는 듀오 모드 게스트가 들어올 수 있어야 하니 일단 인증만 요구
    match /rooms/{room} {
      allow read, write: if request.auth != null;
      
      match /messages/{msg} {
        allow read, write: if request.auth != null;
      }
    }
    
    // 다른 모든 것은 거부
    match /{document=**} {
      allow read, write: if false;
    }
  }
}
